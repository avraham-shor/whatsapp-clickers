# Story 2.1: WhatsApp Webhook Intake and Outbound Dispatch

Status: done

## Story

As the platform operator,
I want verified, idempotent WhatsApp message intake and rate-limited outbound sending,
so that the platform can converse reliably with Participants without losing or duplicating messages.

## Acceptance Criteria

1. **Given** Meta's webhook registration handshake, **when** `GET /webhooks/whatsapp` arrives with the verify token, **then** the challenge is answered correctly (endpoint lives outside `/api`, no session auth).
2. **Given** an inbound `POST /webhooks/whatsapp`, **when** the `X-Hub-Signature-256` HMAC is invalid, **then** the request is rejected and logged; valid signatures are processed.
3. **Given** Meta retries a webhook delivery, **when** the same WhatsApp message ID arrives twice, **then** it is processed exactly once (dedupe by message ID).
4. **Given** outbound messages are queued, **when** the dispatcher sends them, **then** a worker pool with a token-bucket limiter stays under 80 msg/sec, failed sends retry up to 2 times (3 attempts total) with backoff, and final failures are logged WARN without blocking anything. *(Retry count clarified 2026-07-20 code review: "3 attempts total, backoff 1s → 2s" — resolves the earlier "up to 3 times / 1s→2s→4s" wording that contradicted the Task 4 subtask and the tests.)*
5. **Given** any log line involving a Participant, **then** the phone number appears as last-4 only (`phone_last4`), per NFR-4, **and** the local dev workflow (tunnel via cloudflared, Meta test number) is documented in the README.

*Note: requires the Meta WhatsApp Business setup kicked off in Epic 1 — a Meta test number suffices for development. Per the Epic 1 retro (action item 1), Avraham and the dev agent walk through the Meta setup together at the start of this story; the webhook verify handshake succeeding against the test number is that action item's success criterion and part of this story's E2E.*

## Dev Notes

### What this story is — and is not

The WhatsApp transport layer, both directions, with nothing game-shaped in it: webhook verify handshake, HMAC-verified + deduped intake handing normalized messages to a stub, and a rate-limited fire-and-forget outbound dispatcher. It does **not** build: message parsing/routing (`inbound.go` — 2.2), any outbound copy or `messages_he.go` (2.2 creates it; this story sends no user-facing text from app code), JOIN/registration (2.4), `participants` table (2.3), the `game` package (2.3 — **must still not exist** after this story), WebSocket work (2.3), any frontend change (zero web/ diffs). Zero new npm deps; one new Go dep: `golang.org/x/time` (see design decisions).

### Design decisions locked for this story (rationale recorded — do not relitigate)

- **DB-backed dedupe, not in-memory**: Meta retries non-200/timeout deliveries for days; an in-memory set dies on every redeploy mid-retry-window. One tiny table + `INSERT … ON CONFLICT DO NOTHING` (atomic, race-free under concurrent webhook deliveries) is the SM-4-grade answer. `:execrows` 0/1 distinguishes duplicate from first delivery without a read.
- **`wa_inbound_messages` table name**: `wa_` prefix namespaces the transport tables (the glossary covers game domain nouns, not transport bookkeeping); plural snake_case per convention. `wa_message_id TEXT PRIMARY KEY` — Meta wamids are opaque strings, not UUIDs; TEXT PK is correct and the natural key IS the dedupe key.
- **Dedupe-before-handler, 200-always-after-valid-signature**: at-most-once handler invocation, availability over redelivery. If the handler ever fails after dedupe recorded the wamid, Meta already got its 200 and will not redeliver — accepted: from 2.2 onward every reply is best-effort by FR/NFR design (degrade + log WARN, never block). The alternative (5xx to force Meta redelivery) trades a silent-chat risk for a retry-storm risk and violates the "always answer 200 fast" guidance.
- **Dedupe store failure → WARN + process anyway**: a DB blip must not silence the chat (SM-C2 posture: reply guarantees outrank strict once-only). Logged with `dedupe_degraded: true` so NFR-8 observability holds.
- **Consumer-defined interfaces (`Deduper`, `InboundHandler`, `SenderClient`) in `wa`**: exactly the `httpapi.GameStore` precedent — keeps `wa` free of `store` imports and makes every seam stub-testable. Dependency direction stays law: `wa` imports nothing of `httpapi`/`ws`; `main.go` is the composition root; `NewRouter` takes the webhook as an opaque `http.Handler` (no `httpapi` → `wa` import either).
- **Synchronous handler inside the webhook request**: parse + one INSERT + stub call is milliseconds — async machinery (queues, goroutine fan-out) buys nothing until a heavy consumer exists and would complicate the persist-before-ack chain that story 3.3 builds on this seam. Revisit only if 3.x measurements demand it.
- **`golang.org/x/time/rate` as the token bucket** — the single new Go dependency: first-party Go module, zero transitive deps (`golang.org/x/*` already in go.sum via crypto/sync), and it IS the canonical token-bucket the architecture names. A hand-rolled limiter is more code to review for zero benefit. `rate.NewLimiter(70, 70)` shared across all workers bounds the *sustained* rate globally regardless of pool size — see Task 4 for why 70 rather than 80, and note that burst == rate means a straddling one-second window can carry more (documented in `dispatch.go` and deferred). *(Corrected 2026-08-02 code review: this bullet said `rate.NewLimiter(80, 80)` and "global ≤80 msg/s", contradicting the Task 4 bullet and the code, and asserting a per-window guarantee the limiter does not provide. P5 aligned the retry-count wording and missed this sibling.)*
- **Fire-and-forget dispatcher (`Enqueue` returns nothing)**: FR-4/NFR-2 — send failures are logged WARN and never propagate; callers (2.2 replies, 3.2 bursts) must never block or branch on delivery. Queue-full drops rather than blocks for the same reason (capacity 1,000 ≫ any pilot burst).
- **Graph API v25.0 pinned as an overridable base-URL constant**: current version (released 2026-02, ~2-year support window); one constant to bump, tests inject httptest URLs through the same knob.
- **403 for signature failures, 200 for everything authentic**: signature failures are by definition not Meta (wrong secret/forgery/tamper) — rejecting hard is correct and cheap; authentic payloads never get a non-200 (retry-storm avoidance), including unparseable ones (log WARN, drop).
- **No `messages_he.go` in this story**: 2.1 sends no user-facing copy from app code (the live-E2E smoke text is test tooling, deleted after). Creating the file empty would just invite a literal to sneak in outside 2.2's canonical-copy task.
- **Anthropic placeholder validation deliberately deferred to Epic 3**: validating an unconsumed secret breaks boot for zero safety gain — the retro action item's WhatsApp half lands here, the Anthropic half lands with story 3.6 (comment in `config.go` records this).

### Architecture guardrails (violations = rework)

- **Canonical files** (architecture tree): `wa/client.go`, `wa/webhook.go`, `wa/dispatch.go` — exactly these names. `inbound.go` and `messages_he.go` belong to 2.2; creating them here is a scope violation. `redact.go` is a documented addition to the tree (helper, no canonical home named).
- **Dependency direction is law**: `wa` imports stdlib + `x/time/rate` only (its dependencies arrive as interfaces); `httpapi` does not import `wa`; `main.go` composes. `store` remains the only pgx importer.
- **Route**: `/webhooks/whatsapp` outside `/api`, no session auth, HMAC instead (NFR-7). `isReservedPath` already guards SPA fallback for `/webhooks` — do not duplicate.
- **Logging (NFR-8)**: slog JSON, canonical keys — `wa_message_id`, `phone_last4`, `event` context; INFO = lifecycle (accepted, duplicate-skipped), WARN = every degradation (signature reject, retry, permanent send failure, queue drop, dedupe degraded), ERROR = never on a healthy run.
