# Story 2.4: Join the Game with One WhatsApp Message

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Participant,
I want to send `JOIN <code>` and get a welcome reply,
so that I am registered for the Game in seconds (FR-1).

## Acceptance Criteria

1. **Given** a Game in `lobby`, **when** a Participant sends `JOIN <code>` with its valid code, **then** they are registered as a Participant — identified by phone number, display name from their WhatsApp profile name (EXPERIENCE.md A3/OQ-3; a phone whose profile name Meta doesn't supply falls back to its last-4 digits, gender-neutral and correctable) — and receive the Hebrew Welcome reply (name + name-correction hint) per the canonical templates table, **and** the lobby count/list on the dashboard update within 3 seconds via a `ws.Hub` broadcast. *(epic AC-1)*
2. **Given** an invalid or unknown code, **when** a person sends `JOIN <code>`, **then** they receive the Hebrew Invalid-code reply, echoing the code they sent, and no participant row is created. *(epic AC-2)*
3. **Given** an already-registered Participant, **when** they re-send `JOIN` with the same code (including under a Meta webhook retry — already deduped by story 2.1's message-ID ledger before this code ever runs), **then** no duplicate row is created and they receive the same Welcome reply (current display name, not necessarily the one from first registration). *(epic AC-3)*
4. **Given** the `participants` table's existing `UNIQUE (game_id, phone)` constraint (migration `00008`, story 2.3), **then** the new `CreateParticipant` write path is race-safe against it: a conflicting concurrent insert never errors the caller, it resolves to the existing row. *(epic AC-4)*
5. **Given** a Game still in `draft` (lobby not yet opened), **when** a person sends `JOIN <code>` with its valid code, **then** they receive the Pre-lobby reply ("הקוד נכון! ההרשמה עוד לא נפתחה...") and are **not** registered — no participant row, no broadcast. *(epic AC-5)*
6. **Given** a registered Participant (any role, any game state — a phone with at least one `participants` row), **when** they send `שם: <השם>`, **then** their display name is updated (scoped to their most-recently-joined participant row — see Dev Notes) and they receive "עודכן ✓ מעכשיו: [שם]"; **given** an unregistered sender's `שם:` message, **then** they receive the Help reply. *(epic AC-6)*

## Dev Notes

### What this story is — and is not

This story gives `JOIN <code>` and `שם: <name>` real meaning for the first time — until now (`story 2.2`) both were unrecognized text that got the generic Help reply, and `messages_he.go`'s header comment explicitly listed Welcome/Pre-lobby/Invalid-code/Name-updated as "story 2.4". It does **not** build: Spectator registration for JOIN after the game has started (`ErrGameStarted` is an intentional, temporary Help-reply fallback — Story 2.5's entire job is to replace that branch with real spectator logic and the Spectator-notice template); anything from Epic 3 (question dispatch, answer intake, grading, scoring); any dashboard/frontend change (`lobby-page.tsx` already renders `snapshot.participants` generically from story 2.3 — real participant rows just start flowing through the same rendering path with **zero frontend code changes needed**, confirmed by reading the current file).

The visible outcome: a Participant sends `JOIN <code>` from any phone running WhatsApp and is registered within the round trip of that one message; the Organizer watches the lobby's live count/list climb in real time on the dashboard built in story 2.3.

### Design decisions locked for this story (rationale recorded — do not relitigate)

- **`ErrGameStarted` falls back to Help, not a half-built Spectator notice.** The templates table assigns "Spectator notice" to story 2.5; sending an invented approximation of that copy now would ship un-reviewed Hebrew and immediately go stale when 2.5 lands the real thing. The Help fallback keeps FR-2's "no inbound message class results in silence" guarantee intact in the meantime — this is a documented gap, not a bug, and a reviewer should not flag it as one.
- **`שם:` scoping decision: most-recently-joined participant row for the phone, across all games, no broadcast.** The epics/architecture never specify how to resolve "which game" a rename applies to when a phone could theoretically hold rows in more than one game. NFR-3 states the pilot runs "a single Game at a time," so in practice there is exactly one live candidate row; "most recent `joined_at`" is the simplest correct rule under that constraint and degrades gracefully (worst case: it updates a stale/finished game's row, which is harmless). Broadcasting the corrected name to the dashboard was considered and explicitly cut: the epics AC-6 text only requires the WhatsApp confirmation, doing more would mean adding an unscoped-by-organizer game-fetch-by-ID query and a new engine dependency (`SnapshotBroadcaster`) purely for a cosmetic, rare-event freshness improvement (the list already self-heals on the next join, snapshot broadcast, or dashboard reconnect). `[ASSUMPTION]`
- **Fallback display name is the phone's last 4 digits, not a placeholder noun.** Meta's `profileNameFor` (existing, `wa/webhook.go`) already returns `""` when `contacts[]` is absent or has no matching `wa_id` — a real, not hypothetical, case. Every gendered Hebrew noun ("משתתף"/"משתתפת") violates the locked gender-neutral-Hebrew rule (A2); digits sidestep the problem entirely and are trivially correctable via `שם:`, which the Welcome message already advertises. `[ASSUMPTION]`
- **Display names get bidi-isolated (`ltr()`) in every new template, same as JOIN codes.** DESIGN.md/EXPERIENCE.md only name "JOIN, codes, digits" as requiring isolation, but a WhatsApp profile name can be Latin-script (a very real case for mixed-language families — the exact audience this product targets per the brief). Isolating a name that happens to be Hebrew is harmless (a single-direction run's internal character order is unaffected by the isolate's own base direction); isolating one that happens to be Latin is the only thing standing between a correct render and scrambled RTL/LTR reordering on a grandparent's first message from the platform. Applied uniformly rather than trying to detect script at runtime.
- **`CreateParticipant` uses `ON CONFLICT ... DO NOTHING` + a fallback fetch, not a pre-check `SELECT` then `INSERT`.** A check-then-write has a race window; the atomic `INSERT ... ON CONFLICT DO NOTHING` closes it for free and reuses the exact `pgx.ErrNoRows`-means-"no row" idiom every other store method already uses (no new pgconn-error-code handling, unlike `CreateGame`'s join-code-collision retry, which is solving a different problem — regenerate-and-retry, not fetch-the-existing-row).
- **Join-count broadcast is skipped, not degraded-to-a-wrong-number, when the post-insert snapshot build fails.** `OpenLobby`'s existing degrade (story 2.3) returns a snapshot with `ParticipantCount: 0` — which was *true* at that moment (lobby just opened, nobody has joined). The equivalent here would be false: at least one participant (the one who just joined) exists, and 2.3's `emptySnapshot` helper has no way to know the real count without the very `ListParticipants` call that just failed. Skipping the broadcast (leaving `Snapshot` at its zero value, which `wa` checks via `Snapshot.GameID != ""`) is honest; the very next successful join or a dashboard reconnect (`engine.Snapshot`) carries the correct count.
- **`NewInboundRouter`'s signature change has exactly one production call site** (`main.go`) — unlike story 2.3's 30-site `NewRouter` change, this is low-risk; the compiler still catches every miss.
