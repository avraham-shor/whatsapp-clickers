# Story 2.3: Open the Lobby and Watch It Live

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Organizer,
I want to open my Game's lobby and see the participant count and list live on the dashboard,
so that I know when the room is ready.

## Acceptance Criteria

1. **Given** a Game in `draft`, **when** its owning organizer calls `POST /api/games/{gameID}/open-lobby`, **then** the game transitions to `lobby` through `game.Engine.OpenLobby` — the single write path for game state (no handler or store caller mutates `games.state` directly) — and a repeat call, or a call on a game already past `draft`, is rejected `409 GAME_NOT_EDITABLE`. *(epic AC-1, first half)*
2. **Given** migration `00008_participants.sql`, **then** a `participants` table exists with `id`, `game_id` (FK), `phone`, `display_name`, `role` (`CHECK IN ('player','spectator')`, default `'player'`), `joined_at`, and `UNIQUE (game_id, phone)` — created now, populated starting Story 2.4. *(epic AC-1, second half; architecture gap #2)*
3. **Given** an authenticated organizer's browser, **when** it opens `GET /ws?gameId={id}&role=host`, **then**: the `wc_session` cookie is validated before upgrade (missing/invalid → reject, no upgrade); the organizer must own `gameId` (foreign/missing game → reject, no upgrade — same non-enumeration posture as the REST 404s); `role` must be `host` or `display` (anything else → reject, no upgrade); and on success the server immediately sends one `{"type":"snapshot","seq":N,"state":{...}}` message built fresh from Postgres: `gameId`, `state`, `joinCode`, `platformNumber`, `participantCount`, `participants` (empty this story). *(epic AC-2)*
4. **Given** the WS connection drops, **when** `use-game-socket.ts` reconnects with exponential backoff, **then** the next snapshot re-renders current state with no manual refresh, and any received snapshot whose `seq` is lower than the last-rendered one is dropped (UI never regresses). *(epic AC-3)*
5. **Given** the lobby page, **then** it shows the JOIN Code and the platform WhatsApp number (from the new `WHATSAPP_DISPLAY_NUMBER` config) for the organizer to relay to the room, and the live participant count (0 initially) sourced from the WS snapshot — not a separate REST poll. *(epic AC-4)*
6. **Given** the `game` package created in this story, **then** it owns the canonical game-state enum (single source of truth, replacing the ad-hoc local constant in `httpapi`) and is the only package that writes `games.state`; `wa`, `ws`, and `httpapi` never mutate it directly (architecture Enforcement Guidelines). *(structural AC, not in epics verbatim — required by "Emit state changes only through the game engine")*

- [x] **Task 3: `ws` package — hub + handler** (AC: 3, 4)
  - [x] New `server/internal/ws/hub.go`: per-game connection registry. Each registered connection gets its own buffered outbound channel + a dedicated writer goroutine that drains it and calls the coder/websocket write — **coder/websocket connections are not safe for concurrent writes**; serializing every write for a conn through one channel/goroutine is the only safe pattern here (both the initial on-connect snapshot and every later broadcast go through the same channel, so they can never race). `Broadcast(gameID string, snapshot game.Snapshot)`: increments a per-game in-memory `seq` counter (starts at 0; first broadcast for a game → `seq=1`), marshals `{"type":"snapshot","seq":N,"state":snapshot}` once, and pushes the bytes into every registered conn's channel for that game. If a conn's channel is full (slow/stuck client), drop that one write and `slog.Warn` with `game_id` — never block the broadcaster for one bad client (mirrors the dispatcher's "one recipient's trouble never blocks the loop" rule). Export `NewHub() *Hub` and whatever `Register`/`Unregister` shape `handler.go` needs (unexported is fine if same-package).
  - [x] New `server/internal/ws/handler.go`:
    - Consumer-defined `Authenticator` interface: `Authenticate(ctx context.Context, token string) (auth.Organizer, error)` — `*auth.Service` satisfies it directly (same signature as `httpapi.AuthService.Authenticate`; importing `internal/auth` here is fine, it's a foundational package `httpapi` already imports too).
    - Consumer-defined `SnapshotReader` interface: `Snapshot(ctx context.Context, gameID, organizerID string) (game.Snapshot, error)` — `*game.Engine` satisfies it.
    - `func NewHandler(authSvc Authenticator, engine SnapshotReader, hub *Hub, logger *slog.Logger) http.Handler`.
    - Flow: read `wc_session` cookie (same name as `httpapi`'s `sessionCookieName = "wc_session"` — hardcode the literal here, `ws` must not import `httpapi`) → missing/empty → plain JSON 401 (small local `{"error":{"code","message"}}` writer, duplicated ~10 lines rather than importing `httpapi`, which would invert the dependency direction) → `authSvc.Authenticate` → `auth.ErrNoSession` → 401. → read `gameId`/`role` query params; `role` not in `{"host","display"}` → 400; **`gameId` must pass the same UUID-shape check `httpapi.isUUID` uses before it ever reaches the DB** (duplicate the tiny check locally, same reasoning as the error-writer above — [errors.go:59-77](server/internal/httpapi/errors.go#L59-L77) shows the exact logic) → a malformed `gameId` is a 400/404, not a 503; without this guard, pgx's UUID-column type error for non-UUID text surfaces as a scary infrastructure failure instead of a clean rejection. → `engine.Snapshot(ctx, gameId, organizerID)` — this single call both authorizes (ownership) and produces the initial payload; `store.ErrNotFound` → 404 (before any upgrade — a plain HTTP error response, never start the WS handshake for a rejected request). → `websocket.Accept(w, r, nil)` (default same-origin check; see Latest Tech Intelligence on the dev-proxy origin behavior) → register with the hub, enqueue the just-built initial snapshot through the conn's own channel (same serialization path as broadcasts — a small accepted race window if a `Broadcast` lands between building this snapshot and registering means the very first frame could be one step stale; the next broadcast self-heals it, same "accepted pilot posture" class as 2.2's per-recipient throttle decision) → block on a read-discard loop (`for { if _, _, err := conn.Read(ctx); err != nil { break } }`) — the server never expects client-sent app messages (organizer actions are REST-only per architecture), but coder/websocket requires draining reads to detect the client closing and to service control frames; a read error means "connection is over" → unregister from the hub → `conn.CloseNow()`.
  - [x] New `server/internal/ws/hub_test.go`: `Broadcast` fan-out to multiple registered conns for the same game; `seq` increments by exactly 1 per broadcast and is independent per game; a full/slow conn channel drops that write without blocking or panicking (use a small buffered fake conn to force the full-channel case).
  - [x] New `server/internal/ws/handler_test.go`: **must use `httptest.NewServer(handler)` + `github.com/coder/websocket.Dial(ctx, wsURL, ...)`, never `httptest.NewRecorder`** — `websocket.Accept` requires the `http.ResponseWriter` to implement `http.Hijacker`, which `httptest.ResponseRecorder` does not; a recorder-based test panics/errors on `Accept`, not on a real assertion. Cases: valid session + owned game + `role=host` → connects, first frame is a `snapshot` with `seq=1`-or-current and the expected `state` shape; no/invalid cookie → handshake rejected (no successful `Dial`); foreign/missing `gameId` → rejected; malformed (non-UUID) `gameId` → rejected cleanly, not a 503; `role=participant` (or any non-host/display value) → rejected; two simultaneous connections to the same `gameId` both receive a later `hub.Broadcast` call.

## Dev Notes

### What this story is — and is not

The first code to touch live game state: it creates the `game` package (state enum, one transition, a read-only snapshot builder) and the `ws` package (the single realtime channel every live surface will use from here through Epic 4), and gives the Organizer a page to watch the room fill. It does **not** build: the full FR-13 control state machine or "התחל משחק" (Story 3.1 — `live/control-page.tsx`, `game/events.go`, `game/answers.go`, `game/scoring.go` all still don't exist after this story); JOIN/`שם:` parsing or any participant-creating code path (Story 2.4); Spectator logic (Story 2.5); the Audience Display route or any `role=display` rendering (Epic 4 — the WS protocol accepts the query value so the wire contract is right, but no UI consumes it yet); any grading, timers, or question dispatch (Epic 3).

The visible outcome: an Organizer opens a game, presses "פתח לובי", and watches a live (currently empty) participant count that will start climbing the moment Story 2.4 ships.

### Design decisions locked for this story (rationale recorded — do not relitigate)

- **`game` package created now, minimal.** Architecture's Enforcement Guidelines are unconditional: "Emit state changes only through the game engine — no component or handler mutates game state directly." That rule has no story-boundary exception, so the engine has to exist the first moment anything mutates `games.state` outside of authoring (which stays in `httpapi/games.go` — draft-only edits, unaffected). `engine.go` + `snapshot.go` + `state.go` only — no `events.go` (no subscribers exist yet; Epic 3 introduces the event channel when `wa`/`ws` both need to react to transitions), no `answers.go`/`scoring.go`.
- **Snapshot built on demand from Postgres, not cached engine-side.** Architecture: "In-memory hub state is a cache of DB truth — rebuilt on boot, never diverges as source" and "no Redis... always rebuildable from Postgres." At this story's scale (one transition, no timers, no per-question state), there's nothing worth caching in the engine itself — every `Snapshot()`/`OpenLobby()` call reads fresh. The `ws.Hub` caches only the *last broadcast `seq`* per game (ephemeral, resets to 0 on restart — harmless, since a restart also means every client reconnects and gets a fresh snapshot at whatever seq comes next).
- **REST response body for `open-lobby` is the bare `game.Snapshot`, not a new payload shape.** It's exactly what the WS `state` field carries; one TS type covers both the REST response and the socket message, and the frontend doesn't need a second round-trip to render post-transition state (though it gets one anyway via the socket a moment later).
- **`writeStoreError` grows a case for `game.ErrNotDraft` rather than a parallel error-mapping function.** One central domain-error → envelope mapper stays the pattern (`errors.go`'s stated purpose); a second mapper would fork it.
- **`participants.role` values are `'player'`/`'spectator'`, verbatim from the epics/architecture gap note** — this is the one epics-sanctioned exception to the "never `player` as an identifier" glossary rule (the anti-pattern is a `players` table/type name, not a role string inside the correctly named `participants` table).
- **No `CountParticipants` query — `len(ListParticipants(...))` in the engine.** Two round trips (count + list) would cost more than the pilot-scale list ever holds (30-80 rows); one query, one source of truth for both the count and the list in the snapshot.
- **Read-discard loop in `ws.Handler`, not `CloseRead`.** Either coder/websocket primitive works for a push-only server; a plain `for { conn.Read(ctx) ... }` loop is the more explicit, more testable choice (the loop's exit is exactly "the client disconnected," which is what triggers hub unregistration) and doesn't require explaining `CloseRead`'s slightly different contract to a future reader.
- **Small accepted race on the very first frame.** If `hub.Broadcast` fires between `engine.Snapshot()` building the initial payload and the connection registering, the first frame can be one broadcast stale. Documented and accepted (same class as 2.2's per-recipient-throttle decision) rather than engineered away — the very next broadcast (or, worst case, a reconnect) self-heals it, and at pilot scale/human interaction pacing this window is sub-millisecond.

### Latest tech intelligence

- **`github.com/coder/websocket` v1.8.15** (already pinned in `go.mod`; first real usage — currently only a `//go:build pin_deps` blank import in [server/deps.go](server/deps.go)). Key facts for this story:
  - `websocket.Accept(w, r, opts)` requires the `http.ResponseWriter` to implement `http.Hijacker`. **Tests cannot use `httptest.NewRecorder`** — it doesn't implement `Hijacker`, and `Accept` will error/panic against it. Use `httptest.NewServer(handler)` and dial with `websocket.Dial(ctx, "ws://"+addr+"/ws?...", nil)` from the client side of the same package.
  - A single `*websocket.Conn` is **not safe for concurrent writes** — serialize all writes to one connection through one goroutine (a per-connection channel + writer goroutine, as specified in Task 3).
  - The server must keep reading from the connection even if it never expects application messages, to detect client-initiated close and service control frames — a `for { conn.Read(ctx) }` discard loop (or `conn.CloseRead(ctx)`) is required, not optional.
  - Default `Accept` behavior enforces a same-origin check (`Origin` header's host must match the request's `Host`). In `make dev`, the Vite proxy ([vite.config.ts](web/vite.config.ts)) forwards `/ws` with `ws: true` and (by default, no `changeOrigin`) preserves the original `Host: localhost:5173`, which should match the browser's `Origin: http://localhost:5173` — same-origin check should pass unmodified. If local dev hits an origin-mismatch rejection, diagnose the actual Host/Origin values first; do not reach for `InsecureSkipVerify` as a blanket fix (it's a real security control, not local-dev friction).
- **React 19 `useSyncExternalStore`** — first use in this codebase (signature: `useSyncExternalStore(subscribe, getSnapshot)`, both stable across renders — the hook's external store object should be created once per `(gameId, role)` pair, e.g. via `useMemo` or a module-level cache keyed by `gameId:role`, not recreated every render).
